# Flowers N Plants — Corporate E-commerce (UAE)

B2B florist/plant storefront + admin panel for offices in Dubai, Abu Dhabi and Sharjah. Storefront content (products, prices, images, details) is fully admin-managed — no hardcoded product content.

## Stack

- **Next.js 16 (App Router) + TypeScript strict**, Tailwind CSS v4 (CSS-based `@theme`, no `tailwind.config.js`)
- **Supabase**: Postgres + Auth + Storage, RLS on all tables
- **next-intl**: `en` / `ar` with full RTL, path-prefixed locales (`/en/...`, `/ar/...`)
- **Stripe**: Checkout, Payment Links, webhooks; Tabby/Tamara/COD scaffolded
- Next.js 16 renamed `middleware.ts` → **`proxy.ts`** (`src/proxy.ts` here) — this repo does not use the deprecated `middleware.ts` convention.

## Architecture

- `src/app/[locale]/...` — all routes live under the locale segment; `src/app/[locale]/layout.tsx` is the actual root layout (`<html>`/`<body>`, fonts, `NextIntlClientProvider`). There is intentionally no `src/app/layout.tsx`.
- `src/i18n/routing.ts` — locales (`en`, `ar`), default locale, prefix strategy
- `src/i18n/navigation.ts` — locale-aware `Link`/`useRouter`/`redirect` (use instead of `next/link`, `next/navigation`)
- `src/i18n/request.ts` — per-request message loading (`messages/en.json`, `messages/ar.json`)
- `src/proxy.ts` — next-intl locale detection/redirect (Next 16 "Proxy", not Middleware) **and** Supabase session-cookie refresh in the same function, so Server Components under `[locale]/account` see an up-to-date session. Excludes `/auth` (the OAuth/magic-link callback) from its matcher — that route must not get locale-prefixed.
- `src/lib/supabase/client.ts` — browser client (anon key)
- `src/lib/supabase/server.ts` — server client (anon key, cookie-based session, RLS applies)
- `src/lib/supabase/admin.ts` — service-role client, **server-only**, bypasses RLS (webhooks, admin mutations, seed scripts, guest-checkout order writes) — never import into a Client Component
- `src/lib/supabase/types.ts` re-exports `Database` from `types.generated.ts`. Regenerate after every migration change: `supabase gen types typescript --local 2>/dev/null > src/lib/supabase/types.generated.ts` (the `2>/dev/null` matters — the CLI prints a "Connecting to db" line on stdout that corrupts the file otherwise). Check-constrained text columns come back widened to `string`; the data-layer files cast through `as unknown as <Row>` at the query boundary rather than fighting that.

## Design tokens (`src/app/globals.css`)

CSS variables + Tailwind v4 `@theme inline` block: `--color-canvas #FAFBFA`, `--color-surface #FFFFFF`, `--color-ink #0E1512`, `--color-primary #0E7C5A` (emerald), `--color-mint #6EE7B7` (hover/active glow only), `--color-hairline #E9EDEA`, `--color-muted #7A857E`. Fonts: Geist (grotesk, headings/UI) + Geist Mono (`.font-mono-label` — uppercase, letter-spaced, used for all labels/spec lines/AED prices) + IBM Plex Sans Arabic (`ar` locale only, applied via `[dir="rtl"] body`). Use Tailwind's arbitrary-value var syntax, e.g. `bg-(--color-primary)`, since there's no `tailwind.config.js` to extend.

## Conventions

- TypeScript strict; small typed components; Server Components by default, Client Components only where interactivity requires it
- Data access through Supabase migrations, never manual SQL against the live project
- No secrets in code — see `.env.example` for the full list; never commit `.env.local`
- Locale-aware navigation: import `Link`/`useRouter`/`redirect` from `@/i18n/navigation`, not `next/link`/`next/navigation`, so locale prefixes stay correct

## Env vars

See `.env.example`: Supabase (URL, anon key, service role key), site URL, Stripe (secret/publishable/webhook secret), Tabby, Tamara, WhatsApp Business (for sending payment links).

## Data layer (`supabase/`)

- `supabase/migrations/*_schema_tables.sql` — all tables from the brief (`categories`, `products`, `product_images`, `offers`, `customers`, `orders`, `order_items`, `leads`, `blog_posts`, `payment_links`), plus `admin_users` (auth_user_id → role) which the RLS layer and future `/admin` auth depend on. `product_images.alt` is required for the SEO alt-text requirement. `updated_at` triggers via a shared `set_updated_at()` function.
- `supabase/migrations/*_rls_policies.sql` — RLS is enabled on every table. Pattern: public can read `active`/`published` content and everything if `is_admin()` (a `security definer` function checking `admin_users`); admins can read/write everything; storefront enquiry forms can `insert` into `leads` but not read it back. **`orders`, `order_items` and `payment_links` have no public insert/update policy** — checkout and webhook code must write through the service-role client (`src/lib/supabase/admin.ts`), not the anon/browser client.
- `supabase/migrations/*_storage_bucket.sql` — `product-images` bucket, public read, admin-only write (reuses `is_admin()`).
- `supabase/seed.sql` — 2 categories, 8 products (one left `draft` to exercise that status), product images, 2 offers, 2 published blog posts. Images are Unsplash placeholders (`images.unsplash.com` is allow-listed in `next.config.ts`) — swap for real photos via the admin uploader once Phase 5 lands.
- Local dev: `colima start` (or Docker Desktop) then `supabase start` brings up local Postgres/Auth/Storage/Studio and applies migrations + seed automatically. `supabase db reset` re-applies both against the running local stack. `.env.local` already has the local stack's URL/anon/service-role keys (from `supabase status`) — regenerate that file with fresh keys if you ever wipe and reinit the local project, since the demo JWT secret produces new keys each time.
- Against a real project: `supabase link --project-ref <ref>` then `supabase db push` (migrations only — run `psql`/the SQL editor with `supabase/seed.sql` separately if you want the sample content there too).

- `ui/input.tsx` — `Input`, `Textarea`, `Select`, all label/hint/error-aware and id-linked for accessibility
- `ui/card.tsx` — surface shell, hairline border, `soft` prop switches sharp (`2px`) vs. the occasional `12px` radius
- `ui/mono-label.tsx` — the signature uppercase/letter-spaced mono treatment; reused for nav labels, spec lines, prices
- `layout/header.tsx` — Client Component (needs `usePathname`), frosted sticky header, locale switcher via `next-intl`'s `Link`/`usePathname`
- `layout/footer.tsx` — Server Component, TRN + payment marks
- `product/product-card.tsx` — Server Component, the reusable card used everywhere a product is shown. Takes a `ProductCardData` shaped exactly like `products` joined with its primary `product_images` row, so the same component serves the storefront (Phase 4, real Supabase query) and the admin Add/Edit live preview (Phase 5, form state) with zero divergence.
- `src/lib/pricing.ts` — `getEffectivePrice()`/`isSaleActive()` compute the discount/sale-window math once; `formatAED()`/`vatNote()` format for display. Reused by the product card, PDP, checkout and the admin preview — don't reimplement discount math elsewhere.
- `src/lib/utils.ts` — `cn()` (clsx + tailwind-merge)

## Storefront (`src/app/[locale]/`)

- **Routes:** `/` (home), `/shop` + `/shop/[category]` (PLP, filters via query string: `?sort=`, `?tag=`), `/products/[slug]` (PDP), `/cart`, `/checkout`, `/order-confirmation/[number]`, `/setups`, `/corporate`, `/offers`, `/blog` + `/blog/[slug]`, `/account` + `/account/sign-in`. All product/category/offer/blog content comes from `src/lib/data/*.ts` (Server Component-only, uses the RLS-respecting server client) — no hardcoded product content.
- **Cart** (`src/lib/cart/`) is client-only: there's no `carts` table in the schema, by design — a cart only becomes durable data when it's placed as an order. `CartProvider` (in the root `[locale]/layout.tsx`) persists to `localStorage`, hydrating post-mount via `useEffect` (not the `useState` initializer) so SSR and the first client render both start from an empty cart — this is deliberate, not an oversight; see the comment in `cart-context.tsx` before "fixing" the intentional `eslint-disable` there.
- **Checkout → order** goes through `src/lib/actions/orders.ts` (`"use server"`), which uses `createAdminClient()` because `orders`/`order_items` have no public insert policy — this is the one place the service-role client is meant to be reached from the storefront. Only Cash on Delivery actually completes an order today (validated both client- and server-side); card/Tabby/Tamara are visible but disabled pending Phase 6 gateway wiring. The confirmation page also reads via the admin client, keyed by the order number (an unguessable token) rather than by session, since checkout is guest-friendly.
- **Leads** (`src/lib/actions/leads.ts`) insert through the normal anon/server client — RLS explicitly allows public `insert` into `leads` but not `select`, so this one doesn't need the admin client.
- **Account / Auth**: Supabase Auth email-OTP (magic link), no passwords. `src/app/auth/callback/route.ts` exchanges the code for a session and redirects to `/{defaultLocale}/account`; it lives outside `[locale]` and is excluded from `proxy.ts`'s matcher on purpose. First sign-in has no `customers` row yet — `ensureCustomerProfile` creates one (insert allowed where `auth_user_id = auth.uid()`); `updateCustomerProfile` maintains it after. "Recurring" and "Quotes" on the account page are placeholders — there's no `recurring_plans`/`quotes` table in the brief's data model, so this is a deliberate scope boundary, not a bug.
- **Known simplification:** the PDP has no true price-varying size/variant selector because the schema has no product-variants table (not in the brief's explicit data model) — `details` entries (e.g. a "Size" row) are shown as spec info, not a selector that changes price. Flag this if real multi-price variants turn out to be needed; it means adding a table, not a UI tweak.

## Admin (`src/app/admin/`)

- **Not under `[locale]`** — English-only, its own independent root layout (`src/app/admin/layout.tsx`, its own `<html>`/`<body>`). Next.js supports multiple sibling root layouts like this as long as there's no shared `app/layout.tsx` also rendering `<html>`. `proxy.ts` explicitly skips next-intl routing for any `/admin` path so it doesn't get rewritten to `/en/admin`.
- **Auth gate**: `src/app/admin/(dashboard)/layout.tsx` (a route group — doesn't affect the URL) calls `getCurrentAdmin()` and redirects to `/admin/login` if the signed-in user has no `admin_users` row. `src/app/admin/login/page.tsx` sits outside that group so it renders without the sidebar/topbar and without the gate. **Route handlers aren't covered by layouts at all** — `reports/export/route.ts` re-checks `getCurrentAdmin()` itself; copy that pattern for any new route handler under `/admin`.
- **Local admin user**: `scripts/create-local-admin.sh` (needs `supabase status` + the Auth Admin API, since passwords can't go through plain SQL) — creates `admin@flowersandgifts.ae` / `AdminDev123!` linked to an `admin_users` row. Re-run it after any `supabase db reset` from scratch, since `auth.users` gets wiped too.
- **Products Add/Edit** (`components/admin/products/product-form.tsx`) is the flagship piece: a left form + a right live preview that renders the *actual* storefront `ProductCard` fed by current form state via `useMemo`, so there is no separate "preview" implementation to drift from the real card. Images upload directly from the browser to the `product-images` bucket using the signed-in admin's own session (the bucket's admin-only write policy authorizes it) — no upload API route needed. Reordering/removing images and editing `details` rows is local state; **save replaces all `product_images` rows for the product** rather than diffing (`replaceImages()` in `lib/actions/admin/products.ts`) — simple and correct at this data volume, revisit only if products start carrying enough images for that to matter.
- **`ProductCard` has a `navigable` prop** (`components/product/product-card.tsx`) — default `true` for the storefront, must be passed `false` wherever it's rendered outside the `[locale]` tree (the admin preview is the only current case) because its `Link` comes from `next-intl` and throws without an intl context. If a new admin surface renders `ProductCard`, remember this.
- **Local-dev image config**: `next.config.ts` allow-lists `127.0.0.1:54321` (local Supabase Storage) and sets `images.dangerouslyAllowLocalIP` **only when `NODE_ENV === "development"`** — Next 16 blocks image optimization against private IPs by default (SSRF protection), which is correct in production where Storage lives at a public `*.supabase.co` host; only local dev needs the opt-out.
- **Dashboard** charts (`components/admin/dashboard/`) are hand-rolled SVG, no charting library. Colors follow the `dataviz` skill: emerald `#0E7C5A` (brand, single-series revenue line) + blue `#2a78d6` for the second categorical slot — this exact pair was run through the skill's CVD validator (`validate_palette.js`) and passes; don't swap in a different second color without re-validating. A 3rd+ segment folds into a neutral "Other" rather than adding an unvalidated hue.
- **Categories** (`components/admin/categories/category-form.tsx`, under Sell in the sidebar) — added post-launch; the original build only let admins *pick* a category on a product, not create one, so category rows lived in `seed.sql` only. Same shape as Products' image handling but simpler (one image, no gallery): uploads to the shared `product-images` bucket under a `categories/` prefix (no separate bucket — reusing the one bucket keeps the storage policies simple, since both are admin-write/public-read the same way). `position` (int) drives ordering on the home page and the Shop filter pills; the New Category form defaults it to `max(existing) + 1` so new ones append at the end unless you override it.
- **Known gaps, deliberate**: no low-stock panel (products have no inventory/stock-count column in the schema); Settings' Brand/Delivery Zones/VAT/Payment-keys sections are informational (no settings table in the brief's data model) — only Staff & Roles is a real CRUD surface, backed by `admin_users` + the Auth Admin API (`lib/actions/admin/staff.ts`, uses `createAdminClient()` and re-checks `getCurrentAdmin()` itself since the service-role client bypasses RLS entirely).
- **Verified**: a full authenticated Playwright run (login → dashboard → products list/edit/live-preview/image-upload/create/delete → orders → offers → CRM → blog → customers → settings → payment links → reports) passed end-to-end against local Supabase. That surfaced two real bugs, both fixed: `ProductCard`'s hard dependency on intl context (→ the `navigable` prop), and the local-Storage-host image config gap above. Playwright itself was a temporary dev-only install, not a project dependency — there's no test suite wired into `npm test` yet.

## Payments (Stripe live; Tabby/Tamara scaffolded)

- **`src/lib/stripe/client.ts`** — `getStripe()` lazily constructs the SDK from `STRIPE_SECRET_KEY` (throws if unset); `isStripeConfigured()` is the boolean check everything else guards on. Without a key set, card checkout and Stripe Payment Link creation both degrade gracefully (a clear "not configured" message / a manual-URL fallback) rather than crashing — this repo currently runs with **no Stripe keys set**, by design (see Phase 6 status below), so that degraded path is the one actually exercised day to day until real test keys are added.
- **Storefront checkout → Stripe**: `createOrder()` in `lib/actions/orders.ts` always creates the `orders`/`order_items` rows first (status `pending`), same as COD. For `paymentMethod: "card"` it then creates a Stripe Checkout Session (line items priced VAT-exclusive to match `order_items.unit_price`, **plus one extra "VAT (5%)" line item** so the Stripe-charged total matches `orders.total` — don't drop that line item when touching this code) and returns `redirectUrl`; the checkout page does a full `window.location.href` navigation to it (not `router.push` — it's leaving the app). `orders.stripe_checkout_session_id` records which session belongs to which order.
- **Webhook**: `src/app/api/stripe/webhook/route.ts` verifies the signature against `STRIPE_WEBHOOK_SECRET` and is the *only* thing that flips an order to `paid` — the checkout page's `success_url` redirect is not trusted as confirmation, since the buyer can close the tab before it fires. Every status write is guarded with `.eq("status", "pending")` so a duplicate/late webhook delivery can't regress an order an admin already moved further along. Handles both `session.metadata.order_number` (storefront checkout) and `session.payment_link` (admin-created Payment Links) in the same handler.
- **Admin Payment Links** (`lib/actions/admin/payment-links.ts`): creates a real Stripe Payment Link via the API when `isStripeConfigured()` and falls back to the admin manually pasting a URL otherwise — same degrade pattern as checkout.
- **Cart clears on the confirmation page, not at checkout submit** (`components/product/clear-cart-on-mount.tsx`, mounted only in `order-confirmation/[number]/page.tsx`) — this is what makes a cancelled Stripe Checkout land the buyer back on `/checkout` with their cart intact instead of empty.
- **Tabby/Tamara**: scaffold only, documented in `src/lib/bnpl/README.md` — both need a merchant approval process before sandbox credentials exist, so there's no code to run yet, just the integration shape to follow (mirrors the Stripe card flow) when credentials are available.

### Two real bugs this phase's testing caught — both were pre-existing, not introduced by Stripe work, and both are broadly applicable patterns worth knowing before writing the next form or client-persisted state

1. **`CartProvider` had a hydration race** (`lib/cart/cart-context.tsx`): the "have we hydrated from localStorage yet" flag was a `useRef`, which a same-commit write-effect could read as already-`true` (the ref mutates synchronously) *before* the hydration effect's `setItems` had actually re-rendered — so the write-effect fired once with the stale pre-hydration `[]` and clobbered the real stored cart, permanently, on every fresh full-page load (e.g. arriving at `/checkout` directly). Fixed by making the flag `useState` instead of a ref, so the write-effect's guard condition and the hydrated data commit in the same render — see the comment at the top of `CartProvider` before changing this again.
2. **React 19's `<form action={fn}>` auto-resets uncontrolled fields once the action's promise *settles* — including when it resolves to `{ ok: false }` rather than throwing.** Every form in this codebase that reports business-logic failures as a return value, not a thrown error (checkout, the lead-capture form, the account profile form), was silently wiping everything the user had typed on any error — a real, currently-fixed bug, not a hypothetical: `[locale]/checkout/page.tsx`, `components/storefront/lead-form.tsx`, and `components/account/profile-form.tsx` all switched from `<form action={handleSubmit}>` to `<form onSubmit={handleSubmit}>` with `e.preventDefault()` + `new FormData(e.currentTarget)`, which has no such auto-reset. **Any new form built against an action that can resolve to a failure (not just throw) needs this same `onSubmit` pattern, not `action=`.** Fully-controlled forms (every admin form — `product-form.tsx`, `post-form.tsx`, etc., which track each field in `useState` rather than reading `FormData`) are unaffected and don't need it.

## Localization (`messages/en.json`, `messages/ar.json`)

- **Namespaced by page/feature**, matching the pattern started in Phase 1 (`Nav`, `Home`, `Footer`): `Breadcrumbs`, `Emirates`, `Plp`, `Pdp`, `Cart`, `Checkout`, `OrderConfirmation`, `LeadForm`, `Setups`, `Corporate`, `Offers`, `Blog`, `Account`, `SignIn`. Every storefront page/component under `[locale]` now sources its UI text from these — there should be no hardcoded English string left in a Server or Client Component there. `/admin` is deliberately **not** localized (English-only, no `NextIntlClientProvider` — see the Admin section above); don't add `useTranslations` calls there.
- **Server vs Client components**: `getTranslations` (from `next-intl/server`) in async Server Components, `useTranslations` (from `next-intl`) in Client Components and sync Server Components — mixing these up either throws a lint error (`useTranslations` in an async function) or, worse, silently breaks in a component that has no intl context at all (see the `ProductCard`/`navigable` note above from Phase 5 — same root cause).
- **`src/lib/constants/emirates.ts`** is the single source of truth for the 7 emirate values (also `Emirate` in `lib/actions/orders.ts`, derived from it, not duplicated). The **value** stored in the DB (`orders.emirate`, `leads.emirate`) is always the English canonical string (`"Dubai"`, etc.) regardless of storefront locale — only the *displayed* option text is translated, via `t("Dubai")` against the `Emirates` namespace. Same pattern for `LeadForm`'s frequency options (`"Weekly"` etc. stored canonically, translated for display) — admin CRM/Orders stay readable in English no matter what language a lead or order came in through. Follow this pattern for any new enum-like field that's both stored and shown to the visitor.
- **Marketing copy blocks** (Setups' "what we set up"/packages/steps, Corporate's value props/FAQ) are arrays inside the JSON messages, read with `t.raw("key")` and typed with an inline cast at the call site — there's no CMS-backed content for these marketing pages (by design, same boundary as everywhere else: only *products* are required to be admin-managed, not landing-page copy).
- **`ProductCard`'s hover "Add to cart" label is a prop (`addToCartLabel`), not an internal `useTranslations` call** — same reasoning as the `navigable` prop: the admin live-preview renders this component with no intl context, so it can't call the hook itself. All three storefront call sites (`page.tsx`, `plp.tsx`, PDP's related-products section) pass `pdp("addToCart")`; the admin preview uses the English default. If you add a 4th call site, pass this prop or the admin preview keeps working but the storefront one silently shows English.
- **RTL logical properties**: fixed two real instances of directional (not logical) Tailwind classes that would have broken RTL mirroring — the header's cart-count badge (`-right-2` → `-end-2`) and `ProductCard`'s discount badge (`left-3` → `start-3`). Both were verified visually and via computed bounding boxes, not just by reading the class names — `start-*`/`end-*`/`ms-*`/`me-*` etc. are correct in Tailwind v4 without any extra config, but `grep` the codebase for `\bleft-\|`\bright-\|ml-\|mr-\|pl-\|pr-` before adding new absolutely-positioned elements, since nothing catches this at build time. Tailwind's `ltr:`/`rtl:` variants (used for the locale-switcher's border/padding in the header) are the correct escape hatch on the rare occasion a genuinely non-mirroring value is needed instead.
- **Verified**: all 23 storefront routes return 200 in both locales; a targeted content check confirmed real Arabic text renders on every page (not English fallback, not leaked raw message keys); `dir="rtl"`/`lang="ar"` correct; both RTL fixes confirmed via Playwright screenshots and precise bounding-box math, not eyeballing.

## SEO & performance (Phase 8)

- **`src/lib/supabase/public.ts`** — an anon-key client with no cookie plumbing, unlike `lib/supabase/server.ts` which calls `cookies()` and forces every page using it to render dynamically. All storefront-facing read functions (`lib/data/products.ts`, `offers.ts`, `blog.ts`) were switched to this client — RLS still applies (same anon-key permissions a real visitor has), but the pages built on them can now be static/ISR instead of SSR-per-request.
- **`setRequestLocale(locale)`** (from `next-intl/server`) is called at the top of the root `[locale]/layout.tsx` **and** at the top of both `generateMetadata` and the page component on every static-able page (Home, Shop, `/shop/[category]`, PDP, Offers, Blog list/article, Setups, Corporate). Without it, next-intl resolves the locale from request headers on every render, which forces the whole route dynamic regardless of `export const revalidate` — this one call is what actually unlocks static rendering. `export const revalidate = 300` sits alongside it on pages backed by admin-editable data (products, categories, offers, posts); Setups/Corporate have no `revalidate` since they're pure static copy with no DB reads. `/shop` and `/shop/[category]` stay dynamic regardless (they read `searchParams` for sort/tag filters), and PDP/blog-article intentionally have no `generateStaticParams` — new products/posts must render on first visit rather than needing a redeploy, then get cached via on-demand ISR.
- **JSON-LD**: `components/seo/json-ld.tsx` renders a `<script>` tag, escaping `<` so admin-entered content (product names, blog bodies) can't break out of it. `Organization` + `LocalBusiness` render once in the root layout; `Breadcrumbs` emits its own `BreadcrumbList` from the same `items` prop every call site already passes it (no separate breadcrumb data to maintain); PDPs render `Product`/`Offer` (`lib/seo/product.ts`); Corporate renders `FAQPage` from the same `t.raw("faqs")` array the visible FAQ section uses.
- **Canonical + hreflang**: `lib/seo/alternates.ts` → `buildAlternates(locale, pathname)` returns `{canonical, languages}` for the `alternates` field of `generateMetadata`. Every storefront page sets this; `/cart`, `/checkout`, `/account*`, `/order-confirmation/*` additionally set `robots: {index: false}` since they're session-specific or empty-by-default pages with nothing to index.
- **`sitemap.ts`/`robots.ts`** live at `src/app/` (not under `[locale]`) — they're single global endpoints, not per-locale routes. The sitemap queries products/categories/posts via the public client and emits both locale URLs per entry with hreflang `alternates`.
- **`next.config.ts` → `images.qualities`**: Next 16 requires an explicit allowlist for the `quality` prop on `next/image` (default is `[75]` only) — any value not listed is **silently** coerced to the nearest allowed one, no error, no warning in production. `[60, 75]` is configured; `60` is used on the single priority/LCP image per page (first category card on Home, first product card on PLP) to cut bytes, `75` (next/image's default) everywhere else. If a future image needs a different quality value, add it here first or it'll silently do nothing.
- **`--color-muted` was darkened** from `#7A857E` to `#6B756F` — the original failed WCAG AA (3.7:1 against the canvas background, needs 4.5:1) and was used almost everywhere (product descriptions, mono spec lines, footer text). Verified by computing contrast ratios directly rather than guessing; both a Lighthouse accessibility audit and a manual contrast calculation confirm the new value clears 4.5:1 against both `--color-canvas` and `--color-surface`. `--color-primary` and `--color-ink` were already comfortably compliant; `--color-mint` is intentionally exempt since it's glow/hover-only, never text.
- **Heading order**: `ProductCard` renders product names as `<h3>`. Any page that places a product grid directly under its `<h1>` with no intervening `<h2>` fails WCAG's heading-order check — found and fixed on `Plp` (Shop/category pages) and Corporate's value-props section, both via a visually-hidden (`sr-only`) `<h2>` immediately before the `<h3>`s, so the fix is invisible but the DOM order is sequential. Check for this pattern (`<h1>` → grid of cards with their own heading) before adding a new one.
- **Known environment quirk, not a code issue**: Lighthouse's default *simulated* throttling mode gave inconsistent Performance scores (80s–90s) for some dynamic routes in this sandboxed dev container, while `accessibility`/`best-practices`/`seo` stayed a stable 100 across every page tested. Re-running the same pages with `--throttling-method=provided` (real observed timing, no simulation) consistently showed **100 / sub-200ms LCP** — confirming the app itself is fast and the low simulated numbers are a simulation-model artifact of this specific sandboxed environment (shared/virtualized CPU scheduling), not a real regression. The Home page hit a clean **95** even under default simulated throttling. Structural performance work (SSG/ISR via `setRequestLocale` + `revalidate`, `priority`/`quality` on LCP images, minimal client JS) is all in place regardless — re-verify with a normal (non-sandboxed) machine or a real deployment before trusting a simulated-mode score below 95 as a real regression.

## Security rules (do not regress)

- **Never trust the browser for money.** `createOrder` takes only `productId` + `qty`; price, discount, VAT and totals are read from the DB in `src/lib/actions/orders.ts`. Orders are written atomically by the `create_order_tx` Postgres function (service role only).
- **Every admin server action must start with `authorize(...)`** from `@/lib/admin/auth` — server actions are public POST endpoints, layouts don't protect them. Roles: `owner` (all, staff, payment links), `manager` (+ catalog, offers, blog, reports), `staff` (orders, leads, customers). RLS enforces the same via `has_admin_role()`; keep `src/lib/admin/roles.ts` and the policies in sync.
- **Validate all public input with Zod** (`src/lib/validators/*`) and rate-limit with `withinRateLimit()` (`src/lib/security/rate-limit.ts`, Postgres-backed).
- **Order confirmation is looked up by `orders.public_token` (random UUID)**, never by the guessable order number.
- Public tables have no anon write policies (`leads` inserts go through the `createLead` action). Return generic errors to visitors and `console.error` the detail.
- Security headers/CSP live in `next.config.ts`; the proxy only refreshes the Supabase session for `/admin` and `/account`.
- **Product rules** (min qty, min order value, glass vessel + refundable deposit, monthly rental + deposit) live on `products`; all pricing goes through `priceLine()` in `src/lib/pricing.ts`, used by both the cart (display) and `createOrder` (authority). Deposits are outside the VAT base and tracked in `orders.deposit_total` / `deposit_status`.
- **Deploy target is a Hostinger VPS (Docker + Caddy), not Vercel.** See `docs/DEPLOYMENT.md`. Database/auth/storage stay in Supabase cloud. `NEXT_PUBLIC_*` are build args; the service-role key and Stripe keys are runtime env only. Apply `supabase db push` BEFORE deploying new code.
- Store-wide values (WhatsApp, contacts, TRN, hero image) live in the `store_settings` table, edited in Admin > Settings, never hard-coded. Product/category Arabic text is in `*_ar` columns with English fallback (`lib/data/localize.ts`).
